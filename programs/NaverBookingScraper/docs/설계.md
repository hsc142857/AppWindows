# NaverBookingScraper 설계

네이버 예약 파트너센터에 로그인된 Chrome에서 **예약 목록을 한 건씩 수집**해 로컬 SQLite에 보관하고,
**Motospec Visit Import API**로 등록·취소하는 Windows 프로그램 (네이버예약 스크랩).

> 상태: API 연동(연결 테스트·날짜별 목록·단건·일괄 등록/취소·dryRun), 인증키 1회 입력·저장,
> 로컬 저장·전송 현황(전송 완료 / 미전송), GUI 관리 창(Wails)·CLI 구현. 수집(확장 파서)·트레이 상주는 예정.

## 흐름

```
Chrome 확장 (MV3, host_permissions: partner.booking.naver.com)
  └ 알람 → connectNative("com.appwindows.naverbookingscraper") → config(업체 목록·주기)
  └ 업체별 예약 목록 페이지 열기 → parse.js로 Reservation 배열 추출
  └ save {businessURL, reservations}
        ↓ Native Messaging
naverbookingscraper-cli.exe (호스트·CLI)
  └ SQLite: 예약별 최신 내용 해시 — 바뀐 예약만 업로드 대기열에
  └ Visit Import API: POST /api/visit/import-external (200건씩, externalBookingId 멱등)
        ↑
NaverBookingScraper.exe (트레이·관리 창): 업체 관리, 오늘 예약, 새 예약·취소 알림, 서버 목록과 비교
```

DB에 직접 연결하지 않는다. 서버 저장은 Visit Import API가 맡는다.

## Visit Import API (Motospec)

명세: 개발 서버 `http://localhost:3000/docs/visit-import` (OpenAPI `/api/docs/visit-import/openapi`, **v1.3.0**).
기준본: [visit-import-openapi.json](visit-import-openapi.json) — 서버가 갱신되면 새 명세를 받아 이 파일과 비교한 뒤 교체한다.

| 요청 | 용도 |
|---|---|
| `GET /api/visit/import-external` | 연결 테스트 → `{ok, partnerId, partnerName, scopes, allowedPaths}` |
| `GET …?date=YYYY-MM-DD` | 서버에 저장된 그날(서울) 예약 → `{partnerId, partnerName, date, visits[]}` (취소 포함, 최대 500건) — 스크랩 결과와 비교 |
| `GET …?externalBookingId=…` | 예약 한 건 → `{partnerId, partnerName, visit}`, 없으면 404 `not_found` (`date`와 함께 쓰면 400) |
| `POST …` `{items:[…], dryRun}` | 일괄 등록·취소 (최대 200건) → `{dryRun, created, updated, skipped, cancelled, results[], errors[]}` |

- `dryRun: true`면 서버가 DB에 쓰지 않고 건별 예상 결과만 돌려준다 — CLI `import --dry-run`, 관리 창 "미리보기"에 쓴다.
- `results[]`는 건별 결과(`created`·`updated`·`skipped`·`cancelled`·`error`), `errors[]`는 그중 error만(하위 호환).
  클라이언트는 로컬 검증 실패도 `result=error`로 합쳐 **입력 순서대로** 돌려준다.
- 서버는 `scheduledAt`을 UTC(`…Z`)로 돌려준다. 화면에는 서울 시각으로 바꿔 보여 준다.
- 업체(`partnerId`·`partnerName`)는 **GET 응답에만** 온다 (v1.3.0). POST·dryRun 응답에는 없다.

## 업체 확인 (여러 업체가 같은 프로그램을 씀)

인증키는 업체별로 발급된다. 프로그램은 실행할 때 키가 어느 업체 것인지 서버에 물어 확인한다 (`core.CheckPartner`).

- 실행할 때(트레이 앱 시작, CLI `status`·`api set`·`api test`) 연결 테스트로 `partnerId`·`partnerName`을 받아 보여 주고
  `partner.json`(비밀값 아님)에 기억한다. `api show`는 네트워크 없이 기억한 업체를 보여 준다.
- 목록·단건 조회 응답의 업체도 화면 맨 위에 보여 주고 기억을 갱신한다.
- 업로드 전에는 POST 응답에 업체가 없으므로 먼저 `CheckPartner`로 확인해 "<업체>(으)로 보냅니다"를 보여 준다.
- 기억한 업체와 **ID가 다른** 키가 들어오면 "인증키의 업체가 바뀌었습니다: A → B"로 경고한다
  (같은 ID의 이름 변경은 경고하지 않는다). 트레이 앱에서는 이 경우 수집·업로드를 멈추고 확인을 받는 것을 검토한다.
- 인증키를 지우면(`api clear`) 업체 정보도 함께 지운다.

- 인증: `Authorization: Bearer msvi_…` (Motospec 탑바 «인증키»에서 발급, 스코프 `visit.import`).
- 항목(`core.ImportItem`): `externalBookingId`(네이버 예약번호, 1~80자, 멱등 키), `action`(upsert|cancel),
  upsert일 때 `scheduledAt`(ISO-8601)·`phone`(01…) 필수, `name`·`plateNo`·`brand`·`model`·`year`·`mileage`·`requestNote`·`statusHint` 선택.
- 서버는 항목 하나라도 형식이 틀리면 요청 전체를 400으로 거절할 수 있으므로, 클라이언트가 보내기 전에
  `ImportItem.Validate()`로 걸러 내고 오류 목록에 넣는다.

> 2026-10-19: 개발 서버가 v1.2.0(날짜별 목록·단건·dryRun) → v1.3.0(업체명 partnerName)으로 갱신되어 실제로 확인했다.
> 목록 조회를 지원하지 않는 이전 서버(쿼리를 무시하고 핑 응답)는 "예약 없음"이 아니라 오류로 알린다.

## 네이버 예약 → API 항목 변환 (`Reservation.ToImportItem`)

| 네이버 예약 | API 항목 | 규칙 |
|---|---|---|
| 예약번호 | `externalBookingId` | 그대로 |
| 상태 | `action`, `statusHint` | "취소"가 들어가면 `cancel`(예약번호만 보냄), 아니면 `upsert`. 원래 상태는 statusHint(≤40) |
| 이용 일시 | `scheduledAt` | ISO-8601 `+09:00` |
| 예약자 이름 | `name` | ≤40자로 자름 |
| 전화 | `phone` | 숫자만, `+82`→`0`. 휴대폰(01…)이 아니면 로컬에서 오류 처리 |
| 상품 + 요청사항 | `requestNote` | `서비스:<상품>\n<요청사항>`, ≤1000자 |
| 추가 질문 | `plateNo`·`brand`·`model`·`year`·`mileage` | 있을 때만. 연식 1980~2100, 주행거리 0~9,999,999 밖이면 보내지 않음 |

## 인증키 (한 번만 입력)

- 처음 필요할 때(또는 `naverbookingscraper-cli api set`) 한 번 입력받는다. 터미널에서는 화면에 표시하지 않는다.
- 저장 전에 연결 테스트(GET)로 키를 확인하고, 틀리면 저장하지 않는다.
- `%LOCALAPPDATA%\NaverBookingScraper\api.json`(0600)에 저장하고, Windows에서는 **DPAPI**로 암호화한다
  (같은 Windows 사용자만 복호화 — `shared/secret`). 이후 실행에서는 묻지 않는다.
- 화면 표시는 `msvi_****1234`. 키 값은 저장소·로그·오류 메시지에 남기지 않는다.
- Native Messaging 모드는 stdin이 Chrome 연결이라 키를 물을 수 없으므로, 키가 없으면 오류를 보고하고 트레이 알림으로 안내한다.

## 전송 현황 — "GUI에 보이면 전송 완료" (core/store.go)

긁어 온 예약은 먼저 로컬 SQLite(`naverbookingscraper.sqlite`)에 저장하고 바로 전송한다.
**GUI의 "전송 완료"에는 서버가 처리했다고 응답한 예약만 나온다.** 나머지는 "미전송"에 따로 사유와 함께 나온다.

| 상태 | 뜻 | 다음 동작 |
|---|---|---|
| 전송 완료 (`sent`) | 지금 내용이 서버에 반영됨 (`created`·`updated`·`skipped`·`cancelled`) | — |
| 대기 / 변경 대기 (`pending`) | 아직 안 보냈거나, 보낸 뒤 내용이 바뀜 | 다음 전송 때 보냄 |
| 전송 실패 (`pending` + `last_error`) | 서버 연결 오류·5xx 등으로 응답을 못 받음 | **자동 재시도** (GUI 1분마다, 다음 수집 때) |
| 거부 (`rejected`) | 사전 검증 또는 서버가 이 내용을 거부 (`not_found` 등) | 내용이 바뀌거나 "거부 건 다시 전송"을 누를 때까지 보내지 않음 |
| 다른 업체 (`other_partner`) | 긁어 올 때와 지금 인증키의 업체가 다름 | 보내지 않음 (다른 업체에 섞이지 않게) |

- 저장 키는 (업체 ID, 예약번호). `content_hash`는 **보낼 항목(ImportItem)**의 SHA-256 — 보낼 내용이 같으면 다시 보내지 않는다.
- 완료 표시는 `WHERE content_hash = <보낸 해시>` 조건으로 — 보내는 사이 새 내용이 긁혀 오면 완료로 표시하지 않고 다음에 새 내용을 보낸다.
- 내용이 바뀌면 이전 거부 사유를 지운다 (새 내용으로 다시 판단).
- CLI `import`(실제 전송)와 GUI "가져오기"가 같은 저장소를 쓴다. Chrome 확장 수집이 붙으면 호스트가 `SaveScraped` → `UploadPending`을 부른다.

## 확인할 것

1. 파트너센터의 어떤 목록(예약자 관리 / 오늘 예약 / 기간 조회)을 읽을지, 기간·상태 필터, 페이지네이션
2. 목록 데이터 출처: 페이지 DOM vs 페이지가 부르는 내부 JSON 응답 (JSON이면 파싱이 더 안정적)
3. 예약 폼 추가 질문에 차량번호·차종·연식·주행거리가 있는지, 질문 문구
4. 상태 문구 목록 (취소 판정: 현재 "취소" 포함 여부)
5. 운영 서버 주소 (현재 기본값은 개발 서버 `http://localhost:3000`)
6. 같은 내용을 다시 보내도 `updated`로 나오는 경우가 있다 (예: statusHint·연식·주행거리 차이) — 서버의 변경 판정 기준 확인
